# QPix 安全分析报告

- 分析版本：`a6a6dac`（v0.1.2 开发中）
- 分析范围：`backend/` 全部 Go 代码、Dockerfile、docker-compose.yml，前端仅抽查
- 分析方式：静态代码审阅；未执行渗透测试、模糊测试或依赖漏洞扫描

## 总体评价

项目安全基线较高，主要风险集中在**可用性（DoS）**，未发现可直接越权读取或篡改数据的漏洞。

已做到位的部分：

- 全部 SQL 使用参数化查询；排序字段白名单（`recordOrder`）；LIKE 转义
- 会话、Token、分享令牌仅存 SHA-256 哈希；密码使用 bcrypt，并限制 72 字节
- 会话写操作校验 CSRF Token（常量时间比较），Cookie `HttpOnly` + `SameSite=Strict`，并校验 Origin / Sec-Fetch-Site
- S3 凭据、分享令牌使用 AES-256-GCM 加密，并以记录 ID 作为附加数据，防止密文挪用
- 本地存储使用 `filepath.IsLocal` 防路径穿越；前端静态目录使用 `os.OpenInRoot`
- 上传按内容解码校验，像素数在解码前后各校验一次；`MaxBytesReader` 限制请求体
- `X-Forwarded-For` 仅在可信代理链中从右向左解析
- 500 错误不向客户端泄露细节；GORM 日志使用参数占位符
- 容器以非 root 运行，使用 scratch 基础镜像和只读根文件系统，默认只监听 127.0.0.1

## 高风险

### S1. 未认证请求可阻塞全站

`secure()` 在**鉴权之前**获取全局 `policyMu`，写接口获取的是排他锁；`login` 在读取请求体前获取读锁；`serveImage` 在整个图片传输期间持有读锁。

攻击路径（无需任何凭据）：

1. 慢速发送登录请求体，或慢速下载一张公开图片，持有读锁，最长约 2 分钟（`ReadTimeout` / `WriteTimeout`）
2. 发送任意写接口请求（如 `POST /api/v1/albums`，不带 Cookie 和 Origin），进入排他锁等待
3. Go `sync.RWMutex` 在有写者排队时阻塞所有新读者，登录、列表、图片访问全部挂起

建议：

- 先完成身份认证，再获取锁；需要读请求体的接口，在锁外完成 `decode`
- 图片传输不持有全局锁：查到记录、完成权限判断后释放锁，再进行 I/O
- 长期方案：按资源缩小锁粒度，或改用数据库条件更新 / 行锁（PG 的 `SELECT ... FOR UPDATE`）保证一致性

### S2. 限流表满后拒绝所有请求

`limiter.allow` 在条目超过 10000 时对**所有** key 返回 `false`。登录、改密码、分享解锁共用 `loginLimits`。攻击者用大量来源 IP 调用分享解锁接口（IPv6 按 /128 计数，换地址成本几乎为零），即可让管理员在 15 分钟内无法登录。

建议：

- 表满时淘汰最早过期的条目，而不是全局拒绝
- IPv6 按 /64 聚合
- 登录与分享解锁分开计数；增加按账号的失败计数

### S3. 慢速上传占满处理槽位

全局处理槽位只有 2 个，并且在 `ParseMultipartForm` **接收请求体之前**占用。任意两个具有上传权限的 Token 慢速发送数据，即可让全站上传返回 429，最长约 2 分钟。

建议：请求体接收（落临时文件）不占用槽位，仅解码和编码阶段占用；或为上传设置单独的最低传输速率 / 更短读超时。

## 中风险

### S4. 登录用户名时序枚举

用户不存在时直接返回，不执行 bcrypt，两种情况的响应时间相差数十毫秒，可据此枚举有效用户名。

建议：用户不存在时，使用固定的假哈希执行一次 `bcrypt.CompareHashAndPassword`。

### S5. 无密码强度要求

初始管理员密码、用户密码、分享密码都允许 1 个字符。配合 S2 的按 IP 限流（可分布式绕过），弱口令爆破成本很低。

建议：至少要求 8–12 位最小长度，可选拦截常见弱口令；分享密码可单独放宽。

### S6. 相册默认对访客可见

默认相册和新建相册都是 `GuestVisible: true`，上传后匿名即可访问。ID 是 128 位随机数，不可猜测，但链接一旦经 Referer、聊天、日志泄露就无法撤回，只能删图。

建议：在文档中明确说明；或提供全局设置“新相册默认私有”。

### S7. 分享网关绕过全局图片 IP 规则

`requestScope` 对 `/si/` 和 `/api/v1/public-shares/` 返回空范围，`images` 范围的 IP 白名单对分享链接不生效。如属有意设计，请在文档中写明；否则让分享网关同样执行 `images` 范围的 IP 规则。

### S8. 安全响应头不完整

- 无 `Strict-Transport-Security`；如果依赖反向代理添加，部署文档需要明确提醒
- CSP 的 `img-src 'self' blob: http: https:` 允许加载任意外部图片，降低了注入后数据外带的门槛；若无外链图片需求，可收紧为 `'self' blob:` 加上 `public_url`
- `secure_cookie` 默认关闭，公网 HTTPS 部署时容易遗漏

## 低风险

- **S9**：`master.key` 默认与 `qpix.db` 同在 `/data`，一份备份泄露即可解密 S3 凭据。建议文档推荐分开存放、分开备份。
- **S10**：管理员可以把本地存储根目录设为任意可写路径；S3 Endpoint 允许 `http` 和内网地址。管理员是受信角色，风险可接受；可选禁止 `169.254.0.0/16` 等元数据地址。
- **S11**：`QPIX_DISABLE_ACCESS_RULES=true` 关闭全部网络规则，建议启动时输出 WARN 日志。

## 建议修复顺序

1. S1（与性能报告 P1 同一根因，一起处理）
2. S2、S3
3. S4、S5、S8
4. 其余按需处理，或补充文档说明
