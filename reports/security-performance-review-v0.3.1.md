# QPix v0.3.1 安全与性能复核及优化方案

- 审查日期：2026-10-23。
- 代码基线：`v0.3.1`，提交 `04352ca5989c84265d3e901f68e057384ceb894e`。
- 范围：认证、账号与相册权限、Token、分享、图片处理与网关、存储、数据库、上传前端和部署配置。
- 方法：静态审查、Go／npm 依赖扫描、隔离的请求验证、上传生命周期探针和少量编解码计时。
- 本次只输出报告，不修改业务代码，不提交或发布。历史报告保留，本文编号与旧报告独立。

## 结论

当前版本保留了前一轮整改的主要措施：资源权限在数据库查询中限制，写入前重新鉴权，图片权限检查先于 304，慢速接收与编解码槽位分离。此次审查没有确认可直接绕过相册权限、分享密码或管理员身份的漏洞，也没有确认 SQL 注入或 SVG 脚本执行路径。

优先处理上传生命周期和图片处理的资源边界。已复现组件卸载后继续调度上传，以及 80 字节无效 AVIF 触发接口 500。跨账号误上传属于有条件的代码路径推导，尚未用真实双账号浏览器流程验证。复杂图片导致进程内存耗尽的具体阈值也尚未测定。

性能方面，现有游标分页、批量查询和 ETag 可以继续使用。主要改进点是处理槽位覆盖存储 I/O、单图分享重复查询、元数据重复刷新，以及大相册和批量清理缺少分批边界。无需先引入 Redis、消息队列或微服务。

### 已核对的安全措施

| 范围 | 当前实现 |
| --- | --- |

### 图片处理小样本

使用 256×256 合成渐变图，画质 50。各格式先由对应编码器生成输入，再调用当前处理函数；因此输入文件大小、透明度表达和初始编码质量不完全等价。下面的数据用于识别成本，不用于比较画质优劣。

| 原格式压缩 | 单次处理耗时 | 处理期间累计 Go 堆分配 |
| --- | ---: | ---: |
| PNG | 36.1 ms | 1.1 MiB |
| BMP | 3.6 ms | 0.8 MiB |
| TIFF | 3.7 ms | 1.7 MiB |
| AVIF | 154.7 ms | 35.3 MiB |
| HEIC | 41.0 ms | 0.8 MiB |
| JXL | 33.2 ms | 12.3 MiB |

另取 1024×1024 AVIF，识别及解码约 186.8 ms；原格式压缩约 1.25 s，累计分配约 210.5 MiB；转 WebP 约 794.3 ms，累计分配约 156.4 MiB。该进程首次生成 AVIF 样本约 2.04 s，包含编解码器初始化及输入编码成本。

累计分配来自 `runtime.MemStats.TotalAlloc` 的差值，**不是峰值 RSS，也不是常驻内存需求**。采样未控制宿主机其他负载，未重复取分位数，不能线性外推到 400 万像素或 ARM／LoongArch 平台。

## 安全性分析与方案

### S1：编解码缺少独立执行预算

位置：[上传处理](https://github.com/Qwerto107/QPix/blob/04352ca/backend/internal/app/images.go#L185)、[解码与压缩](https://github.com/Qwerto107/QPix/blob/04352ca/backend/internal/processing/processing.go#L59)、[HTTP 超时](https://github.com/Qwerto107/QPix/blob/04352ca/backend/cmd/qpix/main.go#L86)。

接收大小、图片面积和处理并发已有上限。但每个处理槽位没有独立的执行期限或内存预算，HEIC／JXL 的解码上限固定为 1 亿像素，没有从后台当前像素设置传入。上传前的尺寸校验仍然有效；固定内部上限主要缺少对编码尺寸、内部缓冲的进一步约束。

选择保留原文件，也会完整解码以校验内容和生成预览。400 万像素只限制压缩，不能限制完整解码的开销。SVG 的文件大小、节点数和深度限制也不能完全代表路径、滤镜等绘图复杂度。

HTTP `WriteTimeout` 限制网络写入，不能保证第三方编码调用按时退出，语义见 [Go HTTP Server 文档](https://pkg.go.dev/net/http#Server)。AVIF 的当前内嵌实现还使用独立的 `context.Background()`。在请求取消后继续占用 CPU，或者合法大图使进程超出容器内存，均是需要控制的风险；本次未证明具体图片能在默认配置下耗尽内存。

可选方案：

| 方案 | 实施内容 | 成本及边界 |
| --- | --- | --- |
| A，推荐先做 | 将当前像素上限传入支持的解码器；按格式、面积、位深估算在途内存；阶段间检查取消；增加处理耗时和拒绝指标 | 改动中等，保持单进程；无法强制中断不配合取消的库函数 |
| B，需要硬超时时采用 | 用同一 QPix 二进制启动有界工作进程，父进程超时终止，限制工作进程数量和内存 | 无需另装编解码程序；跨平台进程、资源限制和错误恢复更复杂 |

容器硬内存限制和 Go 软内存限制应保留余量。仅设置超时中间件或在外层另起 goroutine，不能解决已经运行的编码计算。

验收：使用静态、动画、多页、高位深及复杂 SVG 样本；取消请求后不再进入后续阶段；记录实际峰值内存；采用方案 B 时确认超时工作进程确实退出。

### S2：上传队列没有随会话结束而停止

位置：[队列调度与卸载](https://github.com/Qwerto107/QPix/blob/04352ca/frontend/src/components/UploadPanel.vue#L153)、[XHR 与 CSRF](https://github.com/Qwerto107/QPix/blob/04352ca/frontend/src/api.ts#L53)、[清理登录状态](https://github.com/Qwerto107/QPix/blob/04352ca/frontend/src/App.vue#L207)。

`onBeforeUnmount` 只释放预览 URL；未取消在途 XHR，也没有停止 `.finally()` 中的 `run()`。探针已确认，组件卸载后仍会启动等待文件。

退出登录后，旧请求仍可能完成并调度后续文件。若用户很快登录另一个账号，后续 XHR 会读取新的 Cookie 和模块中的 CSRF。队列使用“使用我的默认相册”（空 album_id），且存储可用时，存在旧文件进入新账号默认相册的路径。明确指定旧账号相册时，后端所有权校验会拒绝。旧请求的 401 回调还可能清掉新登录状态。

建议：组件销毁或会话切换时停止调度、清空等待项并取消在途请求；为请求绑定会话代次，旧回调不能影响新会话。保持普通页面切换时继续上传的现有行为，页面切换目前使用 `v-show`，不等于组件卸载。

验收：队列 3 张以上，上传中退出、登录另一账号；旧队列不再发新请求，旧错误不使新账号退出。请求已经提交成功的图片不应因前端取消而被误删。

### S3：无效 AVIF 进入 panic 分支

调用入口为 [ConfigReader](https://github.com/Qwerto107/QPix/blob/04352ca/backend/internal/processing/processing.go#L33)。依赖 `github.com/gen2brain/avif v0.6.0` 的 `isobmff.go:142` 在检查 `pitm` 载荷长度之前读取 `payload[0]`。

隔离请求用 80 字节无效容器复现 HTTP 500，错误为 `runtime error: index out of range [0] with length 0`。应用的恢复逻辑接住了异常，未观察到整个进程退出；需要上传身份才能触达，不能描述为匿名远程崩溃漏洞。

建议：修复或采用已核实修复的上游实现；在图片识别／解码边界将可恢复的格式异常转换为格式错误，返回 415，并保留受控诊断。通用 Handler 的 recover 继续作为最后保护。不要通过吞掉所有错误来忽略存储或数据库故障。

验收：空 `pitm`、截断 box、非法属性索引返回 415；正常 AVIF 和含方向信息的图片仍可上传。补少量针对性回归即可，无需先构建大规模测试框架。

### S4：昂贵密码计算缺少全局并发限制

位置：[登录 bcrypt](https://github.com/Qwerto107/QPix/blob/04352ca/backend/internal/app/auth.go#L40)、[分享解锁](https://github.com/Qwerto107/QPix/blob/04352ca/backend/internal/app/shares.go#L387)。

登录和解锁已有每 IP 15 次／15 分钟限制，改密和建分享也有账号限制。bcrypt 已移出全局策略锁，这些整改有效。但大量不同来源仍可同时进入 bcrypt，没有总计算预算。

建议：在原有限流之后增加有界密码计算名额，满时快速返回 429，并避免分享解锁占尽登录预算。保留不存在账号的等成本校验，不通过降低 bcrypt 成本换取吞吐量。名额按目标机器测定。

限流表达到 10,000 项后拒绝新来源，是已有的容量保护；大范围来源仍可能影响新用户登录。需要公网防护时，在外层代理增加总连接／请求约束，不在此处改变已确认的密码规则。

### S5：本地存储缺少符号链接边界

位置：[Local.path／Put／Open](https://github.com/Qwerto107/QPix/blob/04352ca/backend/internal/storage/local.go#L25)。

`filepath.IsLocal` 可以阻止 `..` 等词法穿越，但 `os.Open`、`MkdirAll` 和 `Rename` 仍可能跟随存储目录中的符号链接。攻击前提是能改写宿主机存储目录或共享卷；普通上传者不能控制随机对象路径，也不能据此直接读取任意服务器文件。

建议：存储目录可能与其他进程共享写权限时，采用 Go 的根目录约束文件操作，并保持目录最小权限。外置前端已使用 `os.OpenInRoot`，可以沿用这种边界设计。该措施仍不能替代宿主机对挂载点、设备文件和硬链接的权限管理。依据见 [Go 官方路径约束说明](https://go.dev/blog/osroot)。

## 性能与可靠性分析

### P1：处理槽位覆盖存储写入

位置：[槽位获取](https://github.com/Qwerto107/QPix/blob/04352ca/backend/internal/app/images.go#L185)、[原图和衍生图保存](https://github.com/Qwerto107/QPix/blob/04352ca/backend/internal/app/images.go#L373)。

两个处理槽位从解码前一直保留到上传函数返回，包含原图、预览图、缩略图保存和最后的数据库提交。S3 客户端单次 HTTP 超时为 90 秒；即使 CPU 空闲，两个慢存储请求也会使其他上传无法进入处理。

建议：先在处理阶段完成所需字节或临时文件，释放 CPU 槽位后再保存；保留现有全站 8 个、每账号 2 个在途请求边界和存储引用保护。不可无界保留已经解码的大图来换取并发，也不能提前释放容量预占。

验收：使用可控延迟的测试存储，让两次写入暂停；其他账号能进入有界处理，同时总内存和在途请求仍受限。此项有实际慢存储需求时，比简单增加处理并发更合适。

### P2：单图分享元数据重复查询

位置：[findShare／publicShare](https://github.com/Qwerto107/QPix/blob/04352ca/backend/internal/app/shares.go#L269)。

隔离请求确认，无密码单图分享元数据执行 6 次查询：分享、目标有效性、再次读取目标、再次读取标题、COUNT、分页读取。带密码且已有解锁会话时，还会查询解锁会话。

建议：返回并复用已查询的目标图片，单图响应直接构造 `items` 和 `total`，保留现有返回结构。目标是无密码路径降至 2 次查询，带解锁校验路径约 3 次；这是优化目标，尚未实施测量。密码、到期、撤销、删除状态仍逐请求校验，不能缓存授权结果来减少查询。

### P3：大规模列表与清理缺少分批边界

位置：[全量相册和计数](https://github.com/Qwerto107/QPix/blob/04352ca/backend/internal/app/manage.go#L20)、[首页 COUNT 与兼容 OFFSET](https://github.com/Qwerto107/QPix/blob/04352ca/backend/internal/app/pagination.go#L34)、[清理全量加载](https://github.com/Qwerto107/QPix/blob/04352ca/backend/internal/app/maintenance.go#L45)、[删除相册时读取所有图片](https://github.com/Qwerto107/QPix/blob/04352ca/backend/internal/app/albums.go#L157)。

图片／分享／Token 后续游标页已避免 COUNT 和深 OFFSET。剩余成本来自首页精确计数、相册全量读取及全部 ID 的 IN 查询、待删除图片一次性加载。图片数量较大时，相册计数和维护任务仍可能占用较长查询时间或较多内存。

建议先将后台清理改为按稳定主键分批，防止失败行导致无限重读同一批；相册列表在确有大量相册时提供分页或轻量选项接口。精确总数是否改成按需获取，应作为界面行为选择，不直接删除现有统计能力。

| 数据库 | 当前措施 | 下一步验证与优化 |
| --- | --- | --- |
| SQLite | 单连接、WAL、FULL、UTC 时间、PASSIVE 检查点 | 用大相册计数和批量清理观察连接等待；保留 FULL，不盲目加连接数 |
| PostgreSQL | 10 个连接、用户行锁、复合索引，检测手动安装的 pg_trgm | 对实际查询执行 EXPLAIN ANALYZE；确认短搜索词及 COUNT 成本；扩展继续由 DBA 安装 |
| MySQL | 连接回收、有限预编译缓存、用户行锁、复合索引 | 验证当前版本从零及升级迁移；检查排序是否 filesort、连接等待和前导通配搜索成本 |

按名字／大小排序与按创建时间排序的索引需求不同。应先获取查询计划，再决定是否增加索引，避免写入成本和磁盘占用无谓增长。

### P4：前端重复刷新不相关元数据

位置：[refreshMeta](https://github.com/Qwerto107/QPix/blob/04352ca/frontend/src/App.vue#L238)、[图库元数据读取](https://github.com/Qwerto107/QPix/blob/04352ca/frontend/src/components/LibraryBrowser.vue#L171)。

上传完成后统一刷新相册、统计和上传选项；管理员还会读取设置、存储和全部用户。随后图库刷新又读取相册和统计。250 ms 合并可以减少密集完成时的请求，但持续上传仍会重复拉取不相关管理数据。

建议：上传后刷新图片相关数据；用户、存储和系统设置在对应页面加载或修改后失效。保留现有请求代次校验，可在搜索切换时取消无效请求。先拆分刷新范围，不引入新的前端状态框架。

### P5：预览与实际压缩结果可能不同

位置：[压缩结果替换](https://github.com/Qwerto107/QPix/blob/04352ca/backend/internal/app/images.go#L332)、[后续生成预览](https://github.com/Qwerto107/QPix/blob/04352ca/backend/internal/app/images.go#L377)。

压缩成功后替换了保存的字节，但 `decoded` 仍是压缩前的像素。后续预览图和缩略图继续使用这个对象。低画质原格式压缩或转 WebP 后，用户可能看到更接近输入图的预览，下载却得到颜色或细节不同的文件。

建议：成功采用编码结果后，从最终保存内容生成衍生图；失败回退时继续使用原图。这样会增加一次最终结果解码，需要计入 S1 的预算。后续再考虑由编码器返回最终像素，当前不必为减少一次解码新增通用编解码抽象。

验收：低画质彩色图、半透明边缘与纹理图，分别检查原格式压缩和 WebP；预览对应最终文件。预览本身允许缩放和 JPEG 再编码，不要求逐像素完全一致。

### P6：实际存储占用缺少统计

位置：[主文件用量结算](https://github.com/Qwerto107/QPix/blob/04352ca/backend/internal/app/images.go#L459)、[衍生图生成](https://github.com/Qwerto107/QPix/blob/04352ca/backend/internal/app/images.go#L377)。

用户容量按主文件实际大小计算，预览图和缩略图不计。这与现有产品规则一致，不是鉴权绕过。但低体积 AVIF 等文件生成 JPEG／PNG 预览后，实际存储会大于用户用量显示；大量小文件还受对象数、数据库大小和 inode 约束。

建议先增加全站物理对象大小、待清理对象和临时空间观测，不改变用户配额口径。是否把衍生图计入用户配额、限制相册／图片数量，需要单独确认产品规则。

内存还应计算 tmpfs：最大 8 个接收请求，单张 100 MiB 时，仅上传文件最多接近 800 MiB；默认 20 MiB 时约 160 MiB。它与解码堆、编码器缓冲和应用内存同时存在，不能把 `/tmp:size=1g` 当成独立于容器内存的磁盘。

### R1：文件与数据库的断电一致性

位置：[Local.Put](https://github.com/Qwerto107/QPix/blob/04352ca/backend/internal/storage/local.go#L32)。

本地写入使用临时文件、文件 Sync 和 Rename，能够避免正常请求读到半个文件。但重命名之后没有同步父目录，突然断电时，数据库已提交与目录项持久化仍存在时间窗口。普通上传失败补偿不等同于断电恢复。

建议先评估目标文件系统上的父目录同步，明确不同平台不支持时的处理方式；通过抽样一致性检查发现丢失对象。同步整个目录、并发清理与存储迁移需谨慎设计，本次不建议先引入复杂的持久化任务系统。

## 实施计划与验收

| 批次 | 范围 | 预期结果 | 必要验证 |
| --- | --- | --- | --- |
| 第一批 | S2、S3、P2、P5 | 停止旧会话队列；无效图片返回明确格式错误；减少单图分享查询；预览对应实际文件 | 跨会话队列、畸形 AVIF、分享查询计数、低画质预览各一个针对性验证 |
| 第二批 | S1 方案 A、P1 | 建立图片资源预算，分离处理与存储等待 | 实际照片与复杂格式的小样本压测、慢存储、取消请求和内存峰值 |
| 第三批 | S4、P3、P4、P6 | 限制密码计算并发；分批维护；减少重复查询；观察真实容量 | 登录／解锁并发、待删除积压、大相册、管理员连续上传 |
| 按部署条件 | S5、R1；必要时 S1 方案 B | 加固共享目录和断电恢复；需要时具备硬处理超时 | 文件系统与各发行平台验证，不只在 Windows 上检查 |

每项按独立需求提交。新增压测只使用临时数据，PostgreSQL／MySQL／S3 使用专用测试实例，不连接现有业务存储。

### 建议补充的观测数据

- 上传接收、解码、压缩、预览、存储和数据库提交各阶段耗时；按格式区分成功、回退和拒绝。
- 在途接收数、处理数、预计内存、处理取消数，以及 429／413／415／500 的分类。
- 峰值 RSS、Go 堆、GC、tmpfs 和存储物理用量；累计分配与峰值分别记录。
- 数据库连接等待、每请求 SQL 次数、慢查询及待删除积压。

个人部署可先使用结构化日志和已有进程监控，不要求新增公开监控接口或部署监控平台。日志不记录密码、完整 Token、分享令牌、S3 凭据或原文件内容。

### 保持现有产品与部署约定

本方案不重新提出密码最短长度或复杂度限制，不取消访客直链，不让用户互相授权相册，也不将管理员权限授予个人 Token。分享对直链 Referer／IP 策略的独立性，以及 HSTS 由外层反向代理配置，继续按已确认要求执行。

没有压力数据支持时，不扩大数据库连接池，不增加图片处理并发，不放宽 SQLite 刷盘策略，不缓存权限判断，也不把受限图片改成共享 CDN 缓存。
