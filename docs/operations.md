# 备份、恢复与异常核对

## 备份范围

必须同时备份数据库、所有存储的图片和缩略图、部署配置、`QPIX_MASTER_KEY_FILE` 指向的密钥。S3 对象应单独使用供应商的备份或版本策略。密钥与凭据属于敏感配置，备份应妥善保管。统计中的存储用量仅是 ready 图片保存大小之和，不包含缩略图、数据库、待清理文件和文件系统开销。采用压缩后原文件不再单独保留。

## SQLite 与本地文件

最简单可靠的方式是短暂停止后端写入，备份整个 data 目录或数据卷，再启动。该方式同时保持数据库与文件的一致性。不要只复制运行中数据库的 .db 文件：WAL 中可能还有已提交数据。

Docker Compose 的卷名为 `qpix_data`。从项目根目录执行，先确保 backups 目录存在：

```powershell
docker compose --env-file .env -f deploy/compose.yaml stop qpix
docker run --rm -v qpix_data:/source:ro -v "${PWD}/backups:/backup" alpine:3.23 tar czf /backup/qpix-data.tgz -C /source .
docker compose --env-file .env -f deploy/compose.yaml start qpix
```

如需在线数据库备份，可使用 SQLite Backup API 或 VACUUM INTO；它们只保证数据库快照，图片目录仍需采用一致的快照或暂停写入。首版没有后台在线备份按钮。

## PostgreSQL / MySQL

暂停后端写入后，用 pg_dump / mysqldump 等数据库原生工具备份对应数据库，同时备份图片目录和配置，再启动后端。保留数据库版本和字符集信息。切换数据库类型不等于数据迁移，不能直接把 SQLite 文件交给 PG/MySQL 使用。

## 恢复验证

1. 在独立目录或实例恢复数据，避免覆盖运行中的数据。
2. 恢复原主密钥，确保数据库类型、每个存储目录或 Bucket、文件权限和图片域名配置一致。不要为旧加密凭据生成新密钥。
3. 验证管理员登录、图片数量、相册归属和抽样原图内容。
4. 抽查原图与缩略图外链，再执行一次上传与删除。
5. 验证完成后再安排切换，保留原备份用于回退。

## 异常文件核对

正常上传失败会尝试删除文件并记录清理失败日志。进程恰好在文件保存后、数据库写入前中断，仍可能留下孤立文件。

暂停写入后，按 images.storage_id 分组提取 key、thumb_key，与对应本地目录或 S3 前缀的对象比较：有引用但缺失的文件需从备份恢复；无记录的文件和 `.upload-*` / `.qpix-probe/` 临时对象先隔离核对，确认后再人工清理。不要仅按文件时间批量删除图片。

state=deleting 的记录为待清理项目，服务启动和每 10 分钟会重试。若长期存在，检查存储驱动、磁盘空间、目录权限及日志。不要先删除数据库记录，否则会失去重试所需的对象路径。

## 表结构升级

schema_migrations 保存已应用版本。第 2 版新增存储配置、访问规则和压缩元数据；历史图片 original_size 回填为原 size，文件与链接不变。DDL 逐项检查，支持失败后重试。正式升级前先备份，迁移后不要直接降级二进制；回退应恢复升级前数据库与配置快照。当前仅支持单实例执行启动迁移。
